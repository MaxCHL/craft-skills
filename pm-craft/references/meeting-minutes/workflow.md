# Workflow — 六階段處理流程

每次處理逐字稿都嚴格依下列順序執行。前一階段未完不進下一階段。

---

## Phase 1: Intake（資訊盤點）

**目標**：在動手整理前，先知道有什麼、缺什麼。

### 動作

1. 通讀逐字稿一次，先別動筆
2. 抽取 metadata：
   - **日期** — 找「今天是」「日期」「YYYY/MM/DD」「禮拜X」；相對日期換算為絕對日期（基準：對話的今日）
   - **時間 / 時長** — 「會議從...到...」「開了 N 小時」
   - **與會者** — 自我介紹段、講者標籤、第三人提及「X 也在」
   - **主持人 / Facilitator** — 開場、控時、收斂的人通常是
   - **會議目的** — 開場白前 200 字幾乎都會講
   - **議程** — 「先聊 A，再講 B」「第一個議題」
   - **會議類型** — 依關鍵詞配對 Routing Table
3. 缺漏項目記在 `pending_metadata` 清單，**用 `[需確認]` 標註輸出**，不停下來反問

### 例外（須停下來反問）

只有在以下情況才反問使用者：
- 完全看不出會議主題（逐字稿被截斷、雜訊比訊號多）
- 會議類型嚴重曖昧且影響範本選擇（如同時像產品又像技術討論）

### 輸出

`metadata.md` 草稿區塊：
```yaml
date: 2026-05-14  # [需確認] 推測自開場「今天是禮拜四」
attendees: [王經理, 林工程師, [需確認]]
facilitator: 王經理  # [推測] 開場與收斂皆由其主導
purpose: 確認 Q3 roadmap 與資源分配
type: 產品決策會議
agenda: [Q3 目標, 資源缺口, 競品近況, 下季試行專案]
```

---

## Phase 2: Preprocess（文字清洗）

**目標**：把逐字稿變成可讀的書面語，但**不改變語意**。

### 動作（按順序）

1. **講者標籤統一** — 不同段同一人可能寫成「王」「王經理」「Allen」，全部 normalize 成主標籤（第一次出現的最完整版本），講者標籤格式：`**[王經理]**:`
2. **贅字移除** — 套 `stt-correction.md` 的贅字白名單；含上下文判斷（「對」做附和 vs 「對」做反義）
3. **同音字修正** — 套 `stt-correction.md` 的同音字表 + 領域詞表；不確定者用 `[推測:X]`
4. **標點重建** — 依語氣斷句加逗號、句號；超過 40 字的長句強制拆分
5. **數字 / 日期 normalize** — 「禮拜四」→「2026-05-15 (週四)」，「下個月底」→「2026-06-30」
6. **完全無法判讀的片段** — 標 `[unclear]`，原文存到 Appendix

### 重要

**Phase 2 處理過的逐字稿要保留**，作為 Phase 3-4 的工作底稿。不要修改原始輸入。

---

## Phase 3: Segment（主題切段）

**目標**：把連續文本切成「議程項目」或「主題段落」。

### 切段準則（擇一觸發即切）

1. 主持人說「下一個議題」「接下來討論...」「OK 那這個我們先這樣」
2. 話題明顯轉換（前後兩段討論的對象 / 名詞重疊率 < 30%）
3. 有人提「我們先 break / pause / 暫停」後再回來

### 段落命名

- 若有議程 → 用議程項目名
- 若沒有 → 用該段最常出現的名詞 + 動詞概括（5-10 字）
- 不確定的段落名加 `[推測]`

### 輸出

```
[Topic 1: Q3 OKR 確認] (~ 0:00-0:18)
[Topic 2: 競品 Pricing 反應] (~ 0:18-0:35)
[Topic 3: 工程資源缺口] (~ 0:35-0:50)
```

---

## Phase 4: Extract（資訊撈取）

**目標**：從每個段落抓出**結構化資訊**。

### 必抓清單（每段檢查一輪）

1. **決議（Decision）** — 看判斷句：「我們決定...」「就照 X 來做」「結論是...」
   - 必須有人**明確同意 / 拍板**才算 Decision
   - 沒拍板的丟到 Open Questions
2. **行動項目（Action Item）** — 看祈使句 / 承諾句：「我來做...」「X 之前完成」「下週交...」
   - 抽三要素：Owner / Due / 完成條件
   - 缺任何一項 → 標 `[需確認]`，但仍列入清單
3. **風險與阻礙（Risk / Blocker）** — 看擔憂句：「我擔心...」「問題是...」「會卡在...」
4. **開放問題（Open Question）** — 「這個還沒決定」「下次再看」「待確認」
5. **反對意見（Dissent）** — 即使最後拍板，反對方的理由也要記下（ISO 9001 可追溯性）
6. **關鍵引述（Verbatim Quote）** — 客戶訪談 / 高層發言，2-3 句原文保留

### 抓取產物（Phase 4 內部工作表）

```
Decisions:
  D1: 全力做小兒疫苗 PoC，暫緩成人版
      支持: 王經理, 林工程師
      反對: [推測:張產品] 認為市場規模較小
      生效: 即日起

Actions:
  A1: 王經理 / 2026-05-21 / 完成競品 pricing 比較表 / 關聯 D1
  A2: 林工程師 / [需確認] / API spec 草稿 / 關聯 D1

Risks:
  R1: 醫療廣告法第 X 條 → 需法務 review

Open:
  Q1: 訂閱 vs CPA 比例尚未拍板
```

---

## Phase 5: Assemble（組裝輸出）

**目標**：依 `dimensions.md` 規範把 Phase 4 的結構化資訊組成最終文件。

### 維度產出順序

1. **TL;DR**（最後寫，但放最前）— 3-5 句，從 Decisions + Actions 抽精華
2. **Executive Summary** — 套 SCQA 框架（見 `best-practices.md`）
3. **Detailed Notes** — 依 Phase 3 切段順序展開，每段「背景 / 討論要點 / 結論」
4. **Decisions & Action Items** — 直接用 Phase 4 的工作表，套表格

### 一致性檢查（Phase 5 自我驗證）

- 每個 Action Item 是否關聯到某個 Decision？沒關聯的標「獨立 action」
- TL;DR 提到的決議是否都在 Decisions 表？反之亦然？
- Detailed Notes 的「結論」是否與 Decisions 一致？

---

## Phase 6: Verify & Save（驗收與存檔）

### 動作

1. **彙整 `[需確認]` 清單** — 全文掃描，列在 Appendix「待釐清項目」
2. **彙整 `[推測:X]` 清單** — 同上，使用者可一眼決定要不要採信
3. **彙整 `[unclear]` 原文** — 保留於 Appendix 供使用者比對
4. **檔名生成**：
   - 格式：`YYYY-MM-DD-{slug}.md`
   - slug：從會議標題 / 目的抽 2-4 字關鍵詞，kebab-case，全小寫
   - 範例：`2026-05-14-q3-roadmap.md`、`2026-05-14-vaccine-poc-review.md`
5. **存檔**：
   - 預設位置：`./meeting-notes/`（不存在則 `mkdir -p`）
   - 使用者明說「不要存檔」/「inline」/「貼這就好」→ 不寫檔
6. **回報給使用者**（在對話）：
   - 檔案路徑（若存檔）
   - TL;DR 全文
   - 待釐清清單摘要（N 個 `[需確認]`、M 個 `[推測]`）

### 回報範例

> ✅ 已存到 `./meeting-notes/2026-05-14-q3-roadmap.md`
>
> **TL;DR**:
> 1. 確認 Q3 主推小兒疫苗 PoC，成人版暫緩
> 2. 林工程師負責 API spec，王經理負責競品 pricing 比較表
> 3. 訂閱 vs CPA 比例下週決議
>
> ⚠️ **待釐清 4 項**：
> - A2 林工程師的 deadline 未訂
> - [推測:張產品] 姓名需與會者確認
> - 會議時長未明
> - 法務 review 的 owner 未指派
