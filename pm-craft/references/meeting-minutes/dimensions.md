# 四維度輸出格式規範

每份會議記錄預設都包含這四個維度。使用者可指定縮減。

---

## Dimension 1 — TL;DR（3-5 句）

**用途**：讓沒參加的人在 30 秒內掌握。

### 格式

```markdown
## TL;DR

1. **核心結論** — 一句話總結會議目的與結論
2. **最重要決議** — 1-2 句話帶過 (對應 D1, D2)
3. **最關鍵下一步** — 1 句話帶過 Owner + 時間 (對應 A1)
4. （可選）**未解議題** — 若有重大未決，1 句帶過 (對應 Q1)
```

### 撰寫準則

- **不超過 5 條**；超過代表會議目的不聚焦
- 每條 ≤ 30 字
- 引用編號（D1, A1）讓讀者跳轉
- **動詞優先**：寫「決定先做 X」勝過「討論了 X 的優劣」
- **不出現 `[推測]` `[需確認]`**（這些放後段；TL;DR 只放高把握資訊）

### 範例

✅ Good
```markdown
## TL;DR

1. 確認 Q3 主推小兒疫苗 PoC，成人版暫緩。
2. 試行訂閱+CPA 雙模式，3 個月後依數據決定主軸 (D1, D2)。
3. 王經理 5/21 前產出競品 pricing 比較表 (A1)。
4. 法務 review 的負責人尚未指派，待王經理 5/16 前確認。
```

❌ Bad（太冗、太多猜測）
```markdown
## TL;DR

1. 今天大家熱烈討論了 Q3 的方向，[推測] 主要聚焦在疫苗策略...
（過長，且 TL;DR 不應有推測標註）
```

## Dimension 2 — Executive Summary（一頁式）

**用途**：讓主管 / 利害關係人在 3 分鐘內掌握全貌。

### 寫作框架：SCQA + Decisions + Next Steps

```markdown
## Executive Summary

**會議目的 (Situation + Question)**
{一段話：為什麼開這個會？背景 + 想解決的問題}

**關鍵討論 (Complication)**
- {要點 1：浮現的衝突 / 取捨}
- {要點 2}
- {要點 3 (3-5 個 bullets)}

**主要決議 (Answer)**
- {D1: ...}
- {D2: ...}

**未解議題**
- {Q1: ...}
- {Q2: ...}

**下一步**
- {A1: Owner / Due / 完成條件}
- {A2: ...}

**風險警示**（若有）
- {R1: ...}
```

### SCQA 框架說明

- **S (Situation)** — 已知背景、共識前提
- **C (Complication)** — 出現的問題 / 衝突 / 新資訊
- **Q (Question)** — 需要決定的事
- **A (Answer)** — 拍板的決議

### 撰寫準則

- 總長 ~ 一頁（300-500 字）
- 每個 bullet ≤ 40 字
- 不重複 TL;DR 的字面內容，但結論一致
- 主要決議與下一步的編號要對應 Decisions / Action Items 表

## Dimension 3 — Detailed Notes（依議程逐項）

**用途**：給有參與者複盤、給其他工程師 / 部門深入了解脈絡。

### 格式

```markdown
## Detailed Notes

### Topic 1: {議程主題}

**背景**
{1-2 句帶出為何要討論這個主題}

**討論要點**
- **[角色/姓名]** 提出：{論點}
- **[角色/姓名]** 反對 / 補充：{論點 + 理由}
- **[角色/姓名]** 提問：{問題}
- **[角色/姓名]** 回應：{回答}

**結論**
{對應到 Decisions D# 或 Open Questions Q#}

---

### Topic 2: {下一個議程主題}

(同樣結構)
```

### 撰寫準則

- **每個 Topic 至少有「背景」「討論要點」「結論」三段**
- 討論要點用 bullet，每點開頭標講者
- **保留反對意見**（即使最後沒採納）— ISO 9001 可追溯性
- **不要逐字翻譯逐字稿**，而是濃縮成可讀的論點
- 關鍵發言可用 ` > ` 引用區塊保留原文（最多 2-3 句）
- 結論段必須關聯到後面的 Decisions / Open Questions 表

### 何時保留 verbatim quote

- 客戶 / 使用者的痛點原話（特別在客戶訪談）
- 高層拍板的關鍵句
- 反對方的核心論點（避免被簡化失真）

範例：
```markdown
**結論**
決議採用方案 A (D1)，但保留張產品的反對意見供 3 個月後重審：
> 「我擔心方案 A 的客單價撐不起獲客成本，我們的 CAC 預估是 1500，但訂閱方案的 ARPU 才 800。」
```

## Dimension 4 — Decisions & Action Items

**用途**：執行與追蹤；通常會被複製到 ClickUp / Jira / Notion。

### Decisions 表

```markdown
## Decisions

| #  | 決議 | 背景 / Rationale | 反對意見 | 生效時機 |
|----|------|------------------|----------|----------|
| D1 | 全力做小兒疫苗 PoC，成人版暫緩 | 小兒疫苗市場規模 + 法規進入門檻較友善 | [推測:張產品] 認為成人市場長期更大 | 即日起 |
| D2 | 試行訂閱 + CPA 雙模式 3 個月 | 兩種收費模型風險都不明，需數據 | 無明確反對 | 2026-06-01 起 |
```

#### Decisions 撰寫準則

- **D# 編號**（D1, D2, ...）— 全文一致
- **必填**：決議、Rationale、生效時機
- **可空**：反對意見（無則填「無」）
- 沒拍板的**不放這裡**，放 Open Questions
- 一個決議寫一行；複合決議拆成多行

### Action Items 表

```markdown
## Action Items

| #  | 行動項目 | Owner | Due | 完成條件 | 相關決議 |
|----|---------|-------|-----|----------|----------|
| A1 | 產出競品 pricing 比較表 | 王經理 | 2026-05-21 | 涵蓋 3 家以上競品，含定價、客群、差異化 | D1 |
| A2 | API spec 草稿 | 林工程師 | [需確認] | OpenAPI 3.0 格式，含 auth + 主要 endpoints | D1 |
| A3 | 訂閱 vs CPA AB test 設計 | [需確認] | 2026-06-01 | 含樣本數估算、成功指標、停損條件 | D2 |
```

#### Action Items 鐵三角

每個 Action 必須有：
1. **Owner** — 一個人，不是團隊（「PM 團隊」改成「王經理代表 PM 團隊」）
2. **Due** — 絕對日期（不是「下週」「月底」）
3. **完成條件** — 可驗收的明確標準

**任一缺漏 → 標 `[需確認]`**，但仍列入表中（不能因為資訊不足就漏掉）。

#### 編號連續性

A1, A2, A3 ... 跨議程連續編號，方便引用。

## 附加區塊（每份記錄都有）

### Open Questions / Parking Lot

```markdown
## Open Questions / Parking Lot

- **Q1**: 訂閱 vs CPA 的最終比例如何決定？預計 2026-06 評審
- **Q2**: 法務 review 的時程？待王經理確認後告知
- **Q3**: [推測:張產品] 提的「客單價撐不起 CAC」需後續驗證
```

### Risks & Blockers

```markdown
## Risks & Blockers

| #  | 風險 / 阻礙 | 影響 | Mitigation | Owner |
|----|------------|------|-----------|-------|
| R1 | 醫療廣告法第 X 條 | 上線可能延遲 | 5/20 前法務 review | [需確認] |
| R2 | 競品 Y 已切入小兒疫苗 | 市場窗口縮短 | 加速 PoC 至 8 週 | 王經理 |
```

### Appendix

```markdown
## Appendix

### 標註索引
- 本份記錄共 **3 處 `[需確認]`**、**5 處 `[推測:X]`**、**1 處 `[unclear]`**

### 待釐清項目清單
1. A2 (林工程師的 deadline) — 需 5/16 前確認
2. A3 (Owner) — 需 5/16 前指派
3. R1 (Owner) — 法務 review 負責人未定

### `[推測:X]` 索引
- [推測:張產品] — Detailed Notes Topic 1，可能為「張」姓 PM
- [推測:方案] — 開場段，原 STT「芳安」
- ... (列完所有)

### `[unclear]` 原始片段
- (Topic 2, 約原始逐字稿 03:12-03:18) 「...因為 ◯◯◯ 所以我們要 ◯◯◯」(收音不清)
```

## 維度間的一致性檢查

組裝完成前，最後一輪驗證：

| 檢查項 | 規則 |
|--------|------|
| TL;DR 提到的決議 | 必在 Decisions 表 |
| TL;DR 提到的下一步 | 必在 Action Items 表 |
| Executive Summary 主要決議 | D# 編號需對應 Decisions 表 |
| Detailed Notes 每段結論 | 需指向 D# 或 Q# |
| Action Item 的 Owner / Due | 缺漏者標 `[需確認]` |
| `[unclear]` 原文 | 必在 Appendix 列出 |
| `[需確認]` 全文掃描 | 在 Appendix「待釐清項目」彙整 |

不通過 → 回 Phase 4-5 修正。
